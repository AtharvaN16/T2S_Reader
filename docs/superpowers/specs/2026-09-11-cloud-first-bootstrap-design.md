# Cloud-First Bootstrap with On-Device Handoff

## Goal

A reader who opens the app for the first time hears Kokoro Heart within one
render of tapping play, from the Heroku mirrors, while the on-device Kokoro
engine downloads and warms in the background. Once the on-device engine is
ready, playback hands off to it at the next chapter boundary. No screen, no
key to type, no voice to choose.

## Why

The Eco mirrors are deployed and measured at 0.77x aggregate realtime
(`docs/superpowers/specs/2026-09-11-eco-voice-mirrors-design.md`), and the
app can already render through them. What it cannot do is reach them without
the reader configuring a route by hand and then choosing the hosted voice —
which is the friction the hosted route exists to remove. On-device Kokoro
takes minutes to install on a fresh phone (a 132 MB download, then plan
compilation of 160–200 s on an A19); those minutes are the gap the mirrors
fill.

## Scope

In: the route and key shipped with the app; the hosted voice standing in for
the app's default wherever the on-device route is not available; a
chapter-boundary handoff to the on-device engine within a playback session;
background prepare waiting for the on-device engine.

Out: issuing per-reader tokens (a key in the binary is acceptable for the two
pilot phones and for nothing wider; its own spec); server streaming for a
faster first sound (its own spec); persisting a handoff across sessions; any
store schema change; any change to the server or the mirrors.

## The route ships with the app

`CloudVoiceDefaults` (in `T2SApp`) holds the pilot route: the four mirror
endpoints in order, model `kokoro`, voice `af_heart`, request rate 20.
`CloudVoiceSettings` takes an optional `shipped: CloudVoiceDefaults?`; when
it is given and `UserDefaults` holds no endpoint at all, the shipped values
are written, so the Cloud voices screen shows them and they can be edited,
and the configuration store is active from the first launch. The app also
keeps a marker of the endpoint text it wrote itself; a stored route that
still matches the marker — or, for a build that kept none, one of the
endpoint texts listed in `CloudVoiceDefaults.superseded` — is the app's own
and follows the build, so a phone first launched with four mirrors takes
seven on its next launch. Anything the reader edited, even to nothing, is
never overwritten. The app passes the pilot defaults; tests pass nothing
unless they test the seeding, so every existing settings test keeps its
empty starting state.

## The key

The bearer key travels the way the team id does. `App/Local.xcconfig`
(git-ignored, per Mac) gains `T2S_CLOUD_VOICE_KEY`; `Local.xcconfig.example`
documents it, commented out. `App/project.yml` adds
`T2SCloudVoiceKey: $(T2S_CLOUD_VOICE_KEY)` to both targets' Info.plist
properties, beside `T2SICloudContainer`; the Info.plists are generated by
xcodegen and are not tracked.

`CloudVoiceKeySeeder.seed(infoValue:into:)` in `T2SApp` takes the Info.plist
value and a `SecretStoring`. It stores the value only when the Keychain holds
no key and the value is non-empty and does not begin with `$(` (an unset
build setting reaches the plist as its own name). It returns whether it
stored anything. `AppEnvironment.live()` calls it before anything reads the
route. The key is never logged and never appears in a tracked file.

## The hosted voice stands in

`KokoroVoiceRouting` gains `standIn: @Sendable () -> String?`, defaulting to
`{ nil }`. It is consulted at the two places the routing today lands on the
system voice:

- The app's default voice is requested and the on-device default's route is
  not available: return the stand-in if there is one, else the request as
  before.
- A `kokoro:` voice is requested and its runtime is not available: return the
  stand-in if there is one, else fall back through the default as before.

The stand-in is the cloud route's voice ID
(`CloudVoiceID(configuration:voice:).rawValue`) when a configuration is
active **and** the Keychain holds a key; otherwise nil, so a phone with no
key behaves exactly as today. `KokoroComposition.make` receives the closure
from `AppEnvironment.live()` and passes it to the routing it builds, in both
the Kokoro build and the everyday build; the everyday build therefore reads
with hosted Heart by default rather than the system voice.

`Delivery.applied(to:)` leaves a cloud ID untouched, so the stand-in reaches
the render keys as it is.

## The handoff

`PlaybackCoordinator` gains

```swift
public func handOff(to voiceID: String, fromChapter chapter: Int)
```

which records `voiceHandoff = (fromChapter: chapter, voiceID: voiceID)` and
replans. Every render key and every `RenderRequest` the coordinator builds
takes its voice from `voiceID(forUtterance:)`: the handoff voice for an
utterance whose chapter index is at or past `fromChapter`, the document's
voice otherwise. `load` and `unload` clear the handoff. Chapters before the
boundary keep their cloud keys: already rendered, they are cache hits, and a
seek back into them plays the cloud audio; evicted, they re-render through
the cloud, consistently. A cloud render still in flight for a chapter past
the boundary lands under its cloud key, which no longer matches the expected
key, so the next plan renders that utterance locally and the cloud audio is
simply unused.

`PlayerModel` keeps, per loaded document, the requested voice ID and the
routed voice ID it already stores. On each `tick`, when the chapter under the
playhead has changed since the last tick and the routed voice is a cloud ID,
it resolves the requested voice again; if the routing now answers with a
`kokoro:` ID, it calls `handOff(to: Delivery.applied(to: that), fromChapter:
the new chapter)` and records the new routed voice. Readiness that arrives
during the last chapter produces no handoff in that session.

`RenderScheduler.takeBatch` stops at a change of voice as it already stops
at a change of tier, so a cloud batch (width 4) and a local one (width 1)
never share a lease.

Nothing about the handoff is persisted. On the next load the document
resolves to the on-device voice, cloud-rendered chapters no longer match
their expected keys, and they re-render locally as they are reached — the
library converges to on-device audio on its own.

## Background prepare waits

`PrepareRunner` gains `isStandingIn: @Sendable () async -> Bool`, defaulting
to `{ false }`. When it answers true at the start of a run, the run does
nothing and logs once that prepare is waiting for the on-device voice. The
composition supplies the closure: whether the routing's answer for the
app's default voice is a cloud ID. Prepare therefore never renders a book
through the mirrors on a charger.

## Unchanged

The warm-up veil (a glow behind the text that ends on green; it never blocked
play, and now play means hosted Heart until the green), the Voice screen
(hosted Heart remains a choice by hand), the server, the mirrors, and the
store schema.

## Testing

Unit, before any build:

- `CloudVoiceSettings`: shipped defaults are written once into empty
  defaults and the route is active; a stored endpoint is not overwritten;
  no `shipped` argument leaves the state empty.
- `CloudVoiceKeySeeder`: stores a value into an empty store; leaves an
  existing key alone; ignores an empty value and a `$(T2S_CLOUD_VOICE_KEY)`
  placeholder.
- `KokoroVoiceRouting`: with a stand-in, an unavailable default resolves to
  the stand-in and an unavailable `kokoro:` voice resolves to the stand-in;
  without one, both resolve as they do today; an available default ignores
  the stand-in.
- `PlaybackCoordinator`: after `handOff(to:fromChapter:)`, requests for the
  boundary chapter and later carry the new voice and earlier ones the old;
  a seek back before the boundary reads the cloud key; `load` clears it.
- `RenderScheduler`: a batch never spans voices.
- `PlayerModel`: a chapter change while routed to a cloud voice re-resolves
  and hands off when the routing answers `kokoro:`; no chapter change, or a
  routing that still answers the cloud voice, hands nothing off.
- `PrepareRunner`: a run while standing in plans nothing.

Live, on the 17 Pro:

1. With the key in `App/Local.xcconfig`, the Phone build installs; the Cloud
   voices screen shows the four endpoints and "Cloud route active".
2. With the on-device model removed (a fresh install, or the model directory
   cleared), open a book and tap play within ten seconds of launch: Heart is
   heard from the mirrors within one render; the veil is still warming.
3. The veil turns green; at the next chapter boundary the voice continues
   without an audible seam, and the mirrors' logs show no request for that
   chapter or later.
4. Seek back into a chapter before the boundary: it plays without a new
   request to the mirrors.

## Acceptance

Accepted when the unit tests above pass, the existing suites pass unchanged,
the app builds for both schemes, and live checks 1 to 4 hold. If the handoff
is audible or the first sound fails, the stand-in is disabled by removing the
key from `Local.xcconfig` and rebuilding; nothing else needs undoing.

## Constraints

- Basic mirrors, $49 a month for seven, as decided on 2026-09-12 so the route is
  always warm and ahead of playback; the mirrors and their script are otherwise untouched.
- The key never appears in a tracked file, a log, or a test fixture.
- Two phones only, until per-reader tokens exist: every reader's first
  minutes draw on the shared Eco pool, and a key in the binary can be read
  out of it.
- No store schema change: the handoff lives in the session.
